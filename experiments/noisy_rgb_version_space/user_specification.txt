## 4. 二値 out_same を状態同値として使わない

旧方式:

```python
same = z <= T
```

をそのまま状態の同値関係として使ってはいけません。

pair comparisonは必ず

```text
SAME
DIFFERENT
UNRESOLVED
```

の3値を返してください。

### 初回比較

既存と同じ独立RGB batchを使います。

現在の既存score

```text
z(x,y)
```

と既存calibration threshold `T` 自体は、最初の実験では変更しません。

ただし1回の `z <= T` / `z > T` だけで確定してはいけません。

### 再測定

同じ2 historyについて独立noise namespaceで再撮影します。

固定stage:

```text
8 exposures / history
16 exposures / history
32 exposures / history
```

とします。

途中結果を見て回数を増減しないでください。

各stageで独立replicate comparisonを保存してください。

### 三値判定

少なくとも、

```text
すべての独立replicateが T より十分同側
```

でなければhard SAME / DIFFERENTへ落とさないでください。

具体的なconfidence ruleは実行前に `PROTOCOL_VS.md` に数式で固定してください。

重要:

- 一度でも判定が安定しなければ即splitしない。
- UNRESOLVEDは失敗ではない。
- UNRESOLVEDを新state追加と同じ処理へ流さない。
- 閾値を結果を見て変更しない。
- confidence ruleをfresh run開始後に変更しない。

## 5. group_index ではなく candidate set を持つ

新実装では、

```python
group_index(history) -> int | None
```

を中心にしないでください。

代わりに概念的に、

```python
candidate_states(history) -> set[state_id]
```

を持ってください。

各既存代表state `r` について、

```text
compare(history, r) == DIFFERENT
```

なら候補から削除。

```text
SAME
UNRESOLVED
```

なら候補として残す。

従って、

```text
candidate count = 0
```

と

```text
candidate count > 1
```

を同じ処理にしてはいけません。

## 7. 候補が複数の場合

これが今回の中心です。

```text
candidate set = {q1,q2,...}
```

をそのまま保持します。

access historyを追加して逃げないでください。

### 7.1 まず追加撮影

8→16→32 exposureで候補を再評価します。

DIFFERENTになった候補だけ削除します。

### 7.2 それでも複数なら active action probe

候補集合を最も分けそうなactionを選んでください。

action alphabetは既存のものだけです。

最初はdepth 1:

```text
[a]
```

を全actionについて評価。

必要ならdepth 2:

```text
[a1,a2]
```

まで候補にします。

depth 3以上は今回のprimary protocolでは使わないでください。

各probe `e` について、

```text
現在のcandidate statesが
probe後に何種類の予測観測へ分かれるか
```

を、既に獲得済みのRGB evidenceとtransition evidenceから計算してください。

選択基準は実行前に固定し、例えば

```text
expected remaining candidate count
```

が最小のprobeを選びます。

同点はaction IDの辞書順など固定規則にしてください。

### 7.3 probeを実際に実行する

target historyとcandidate代表historyについて、

```text
reset
→ replay history
→ selected action probe
→ noisy RGB再撮影
```

を実行します。

結果が DIFFERENT になったcandidateだけ削除してください。

候補1個になるか、固定probe budgetに達するまで繰り返します。

## 8. それでも判定不能なら保留する

probe budgetを使い切っても

```text

```

なら、

```text

```

としてqueueへ残してください。

**新状態を捏造しないでください。**

後で新しいsuffix・新しいtransition evidenceが増えたら再評価します。

同じunresolved entryを無限に回さないよう、

```text

retry_count
```

を記録し、evidenceが増えていない場合は再試行しないでください。

## 19. Scopeと、なぜ現時点では一般ゲームまで証明したことにしないか

今回の実験条件は、

```text
有限状態に落とせる3D world
reset可能
action alphabet有限
physicsは決定論的
RGB sensorだけ確率的
同じaction historyを何度も再実行可能
```

です。

この条件では、

```text
reset
→ 同じaction historyを再生
→ 別noiseで再撮影
```

を繰り返せるため、

**RGBの違いが本当にworld-stateの違いに由来するのか、それとも撮影noiseだけなのか**

を独立再観測で検査できます。

これは今回のversion-space方式にとって重要な能力です。

一方、Minecraft/FPS級の一般環境では、今後さらに次の問題が入ります。

### 19.1 完全resetできない環境

実ゲームでは、

```text
敵AIの内部状態
他プレイヤー
乱数
破壊された地形
物理シミュレーションの微差
```

などにより、同じ世界状態へ完全に戻って再撮影できない場合があります。

その場合、

```text
同じhistoryを再実行して比較
```

という現在の検査方法をそのまま使えません。

将来的には、

```text
reset/replay型の状態同定
```

から、

```text
オンラインbelief-state更新
```

へ一般化する必要があります。

### 19.2 確率的なworld dynamics

今回のphysicsは、

```text
(state, action) -> next_state
```

が固定です。

一般的なゲームでは、

```text
P(next_state | state, action)
```

として扱う必要がある場合があります。

その場合、「同じpredictive state」の定義も、

```text
同じactionをすると同じnext stateになる
```

ではなく、

```text
同じaction列に対して同じ未来分布を生成する
```

へ一般化する必要があります。

### 19.3 連続状態

今回の位置・heading・jump状態は有限状態として扱えます。

実FPSでは、

```text
continuous position
continuous velocity
continuous camera rotation
projectile trajectory
physics values
```

など、ほぼ連続な状態空間になります。

その場合、有限個のstate IDだけで表現するのではなく、

```text
局所的なpredictive equivalence
continuous predictive state
```

または階層的なstate abstractionが必要になる可能性があります。

### 19.4 任意camera

今回比較するcamera条件は、

```text
base
(.32,-.24) pixel shifted
```

のみです。

これは画像平面上の固定された微小offsetであり、

```text
任意の3D camera position
yaw
pitch
roll
FOV
occlusion
first-person / third-person
```

への一般化を確認したものではありません。

したがって将来はcameraそのものをlatent nuisanceとして扱い、

```text
cameraが違ってもaction-conditioned futureが同じなら同じworld state
```

と認識できるかを別に検証する必要があります。

### 19.5 自然画像・複雑texture

現在は人工的な3D rendererです。

Minecraft/FPS級では、

```text
高解像度texture
lighting
shadow
particle
animation
UI
motion blur
大量のobject
```

が入ります。

今回のRGB分布比較がそのまま十分とは限りません。

ただし、今回の実験はこれらが不可能だと示すものではありません。

目的は、

```text
noisy visual observation
+
action-conditioned future
+
active experiment
```

だけからpredictive stateを構成できるか、最小条件で原理を確認することです。

この有限・reset可能な条件で成立した後、

```text
resetを弱める
→ dynamicsを確率化
→ cameraを連続化
→ stateを連続化
→ rendererを複雑化
```

と一つずつ制約を外していくことで、Minecraft/FPS級への一般化可能性を段階的に検証できます。

したがって最終報告では、

```text
Minecraft/FPS一般へ使えない
```

とは書かず、

```text
今回確認したのは有限・reset可能・決定論的physics +
確率的RGB sensorの条件までである。

より一般的な3Dゲームへ進むために、次にどの仮定を外す必要があるかが明確になった。
```

と記述してください。

## 20. この実験で確認したいこと

確認したいのは、

```text
画像を一度見てstate IDへhard assignmentする
```

方法ではありません。

確認したいのは、

```text
noisy RGB
→ candidate predictive states
→ UNRESOLVEDを保持
→ 必要なものだけ再撮影
→ 必要ならactionを自分で試す
→ impossible candidatesだけ削る
→ 確定した証拠を蓄積
→ predictive state machine
```

という閉ループです。

**「分からない」を保持できること自体を学習機構の一部として検証してください。**

Codexは結果に合わせて別方式を考案せず、この固定比較を最後まで実行してください。
