`corcondor/mortra` の現在の Noisy RGB Predictive V2 を基準に、**provisional family compression のみを追加した比較実験**を実装・実行してください。

目的は状態同一性の条件を緩めることではありません。

目的は、

```text
同じ／非常に近い未確定仮説を表す多数の provisional history が、
同じ識別実験を何度も重複実行している可能性
```

を検証し、

```text
state identity は別々のまま保持しつつ、
探索・probe・証拠要求だけを family 単位で共有
```

したとき、状態獲得効率が改善するかを測定することです。

## 3. provisional family の意味

familyはstateではありません。

```text
family membership != state identity
family membership != merge
family membership != SAME certificate
```

です。

各provisional historyは従来どおり独立した

```text
PredictiveNode
```

として保存してください。

familyは、

```text
「次にどの証拠を取りに行くか」
```

を共有するためだけの探索単位です。

---

## 4. family signature

hidden state / true classを一切使わず、現在までの公開証拠だけでfamilyを構成してください。

初期案として、以下の組をfamily signatureとしてください。

```text
(
    sorted existing candidate representative IDs,
    NEW possible flag,
    public-label signature of already sampled endpoints,
    observed outgoing-action mask,
    known local SAME/DIFFERENT/UNRESOLVED pattern,
    already tested distinguishing suffix set
)
```

履歴そのものやhidden state IDをsignatureに入れないでください。

RGBのnearest-neighborだけでfamilyを作らないでください。

---

## 5. familyを作ってもnodeを統合しない

同じfamilyに

```text
h1
h2
h3
...
```

が入っても、

```text
h1 == h2
```

とは扱わないでください。

各nodeの

```text
history
outgoing transitions
certificates
candidate set
merge status
```

は別々に保持します。

family側に保持してよいのは、

```text
- 次に試すprobe候補
- probeの優先順位
- 既に情報量が低かったprobe
- candidate pairを分離した既知のsuffix
- 必要な未取得証拠の種類
```

です。

---

## 6. probe sharing

現在のV2では、多数のprovisional nodeが同様の31実験を個別に繰り返します。

Bでは、family内で

```text
次にどのprobeを試すか
```

を共有してください。

例えばfamily内で

```text
jump
```

がcandidate setを全く縮めなかった場合、

その情報をfamily-level schedulingに利用し、別nodeでも優先順位を下げて構いません。

ただし、

```text
h1で得たSAME certificateを
h2のSAME certificateとして流用
```

してはいけません。

**証拠そのものはhistory-specificのまま**です。

共有するのはprobe selection policyだけです。

---

## 7. local distinguishing certificate sharing

既知の

```text
(q7, q13, suffix=[forward])
```

のような代表state間のDIFFERENT certificateはfamily内で再利用して構いません。

つまりcandidate setに

```text
q7, q13
```

が同時に残るfamilyでは、

```text
forward
```

を高優先度probeとして再利用できます。

ただし実際のtarget historyに対する比較RGBは必ず取得してください。

---

## 8. family split

family内のnodeで新しい証拠が得られ、

```text
candidate set
public label
observed transitions
known difference pattern
```

が変化した場合、そのnodeを自動的に別familyへ移してください。

family構造は可逆・動的で構いません。

---

## 9. family saturation

同一familyについて、

```text
新しいcandidate exclusionなし
新しいrepresentativeなし
新しいdistinguishing witnessなし
```

が固定回数続いた場合、

```text
FAMILY_SATURATED
```

としてprobe優先度を下げてください。

これはstate mergeではありません。

後で新しいrepresentative / certificate / counterexampleが増えれば再activateしてください。

固定回数は実行前protocolで決め、結果を見て変更しないでください。

## 15. 成功判定

BがAより良いとするのは、少なくとも以下のどれかが同じresource checkpointで改善した場合です。

```text
represented true classes ↑
exposures per represented class ↓
heldout unresolved ↓
confirmed state count ↑
control success ↑
```

かつ、

```text
wrong unique
wrong empirical merge
transition error
```

を悪化させないこと。

provisional node数が減っただけでは成功としないでください。

## 16. 重要な失敗パターン

以下も結果として保存してください。

### family ≈ node

```text
family_count ≈ provisional_count
```

なら、単純な重複探索が主因ではない可能性があります。

### familyは小さいがmixedが多い

family圧縮signatureが粗すぎます。

### pure familyが巨大なのにprobe量が減らない

probe-sharing実装が効いていません。

### probe量は減るがrepresented classが増えない

センサ情報量またはSAME確定が次のボトルネックです。
