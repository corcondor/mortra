# Active-Frontier Reconnection: Frozen Paired Protocol

## Question and permitted change

Does returning already acquired concepts to the existing active frontier create
later certified dependencies or improve held-out performance under a fixed
resource bound? No solver, prover, concept grammar, theory engine, procedure
synthesizer, retrieval index, or scheduling strategy is added.

The original mathematical baseline is
`f9f80e39ca92035bfc37490ad5a072289c9cd80f`. The earlier long-run, Actions
`34720836699`, is diagnostic context, not evidence for this new paired run.
The earlier report is `docs/research/persistent-learning-longrun-20260913.md`.

Inspection found `add_concept` and `derive` refresh the active set, but exhaustion
of the active set does not. `actions` offers `invent` using only that active set.
The patch calls the existing `refresh_active` when pending terms and unexpanded
active concepts are both exhausted. The existing least-visited-then-cost policy
still chooses the action. Two events record active-set refresh and actual parent
expansion. There are no domain, concept ID, or mathematical-answer special cases.

## Fixed before either learning arm starts

The driver is `scripts/measure_frontier_reconnection.py`. It freezes both plans,
both domain configurations, evaluation questions and their hashes, and K0
evaluations before starting either learning arm. It checks exact checkout SHAs
and identical domain configurations. Normal runs use the existing
`scripts/run_theory_formation.py` entry and its source/config-checked resume.

- Domains: `theory-ring`, `theory-fold-frames`.
- Condition: normal learning, same in both arms.
- Training seed: 20260913; held-out seed: 739182.
- Unchanged original long-run budget: 12000 cycles, 600 engine seconds,
  16000 candidates, 128 concepts, 32 active concepts, term size 9,
  4 representation records. Other domain settings are unchanged.
- Checkpoints: 0, 10, 25, 50, 100, 250, 500, 1000, 2000, 4000, 8000, 12000.
- Evaluation: existing `make_suite`, 8 contexts, 64 ordered questions/domain,
  3 repetitions. Questions and oracle answers never enter the learning process.
- Added evaluation resource bound: an individual exact-prover input may contain
  at most 32 abstract-syntax-tree (AST) nodes, counting both sides together.
  The bound is enforced before the existing prover runs. Certified rewrites
  may reduce that input or discharge the equality without a prover call.
- K0 must include both solved and budget-exceeded questions. Otherwise the
  driver stops; it must not retune questions or the bound during the experiment.

This is a proof-input budget, NOT a total CPU, wall-time, or matching budget.
It measures bounded capability, not discovery of previously unknown theorems.
The old unbounded suite was already solved at K0. Unbounded final evaluation is
also retained. All questions are generated by pre-existing evaluator code.
The fixed external task sequence is identical. Internal self-generated tasks
may diverge because the restored frontier is exactly the intervention tested.

## A, B, C and the before/after comparison

A is fresh K0, B is final Kt, C is a discarded evaluation copy of Kt with a
used acquisition disabled. Each arm includes all-rule, earliest-used-rule, and
rule-plus-descendants ablations. A further ablation selects the earliest used
theorem descended from a newly expanded formerly dormant concept. If none is
used, that absence is recorded, not replaced by a hand-picked theorem.

Both mathematical checkouts run afresh in the same Actions job. Distinguish
K0-to-Kt improvement already present BEFORE the patch from the additional
AFTER-minus-BEFORE effect of the connection. Retain failure and budget-exceeded
outcomes. An ablation that loses a solved task is evidence of causal dependence
under this evaluation protocol, not independent novelty evidence.

## Required outputs and limitations

Per-concept JSON traces cover every concept unexpanded at the fresh before-arm
stop. They record acquisition/storage, eligible syntax under the existing
composer and limits, active insertion, scheduler selection, expansion, and
recorded child-concept/theorem dependencies. Old inactive algebra concepts at
the AST cap have no legal syntactic continuation; do not label them all wiring
failures. Unrecorded historical insertion or binary-operand provenance must not
be inferred. Old parent links record the expanded parent, not a complete DAG
of every operand's ancestry.

Per-cycle CSV/JSON retains knowledge sizes, semantic representation families,
reuse, theorem dependency depth, held-out solved count, inspected rule
candidates, prover calls/input nodes, engine seconds and wall time. Evaluation
records actual rewrite-call duration separately from exact certification time
and state-copy time. Timing wrappers exist only in discarded evaluations.
For blocked prover calls, the existing solver does not yet save rewrite
dependencies: those rows explicitly mark the missing dependency record.

The concept/representation caps are NOT enlarged. If the archive is full,
zero new concepts or representations does not diagnose a deficient language.
New theorems can still be generated and verified from returned concepts.
The stored-space route is unchanged; `Theory.settle` does not newly route its
held-out equalities through those spaces. One seed is not robustness evidence.

## Execution and shared evidence

Use the existing **Verify MORTRA Kernels** workflow, `worker-ci.yml`, dispatch
suite `frontier-reconnection`. Set `target_ref` and `expected_sha` to the same
full committed patch SHA, and dispatch from its branch. The job also repeats
the 351 q-directed tests, normal acquisition, stored reuse and legality refusal,
plus theory and measurement guard tests. Release CI is unchanged.

Equivalent driver command after checking out both immutable commits:

```bash
python scripts/measure_frontier_reconnection.py --before /path/to/baseline --after /path/to/patch --expected-after FULL_PATCH_SHA --output /new/output
```

The artifact contains both fresh learning runs, exact commands/configs, source
seals, environment versions, every checkpoint, independent replay checks,
per-question evaluations and ablations, per-concept traces, and the paired
`frontier-reconnection/verification.json`. Workflow run ID and both SHAs are
recorded. No old success logs substitute for execution.
