Prepared for Codex. This records what runs today, how to run it, what is proved,
what is only finite-checked, and which earlier claims have been withdrawn. It is
not a claim that the work is correct; it is a description of what exists.

`THEORY.md`, beside this file, states the nine points the representation layer

---

## 1. What the user is asking for

**The general algorithms may be implemented by the developer.** Writing a
closure prover, a counting lemma, a certificate checker or a search harness is
normal development work.

**During a test, MORTRA does the candidate generation, representation
acquisition, verification and reuse.** The developing agent does not inject the
answer, the observable, the basis, the action matrices, a candidate identifier,
or an auxiliary quantity part-way through a run. If a defect is found mid-test,
the fix goes back into development and the run is repeated as a *new* run rather
than patched while it executes.

The distinction that matters: a lemma written into the code before any run is
general knowledge the system uses. A quantity supplied during a run because the
run needed it is an injection, and invalidates the run as evidence of autonomy.

## 2. Entry points, and what calls what

### 2.1 Normal entry — solve tasks end to end

```
scripts/run_representation_tasks.py                       <- the normal entry
  └─ self_directed_search.solve(task, ...)
       ├─ fold_observable_system.verify_step              premise, re-proved
       ├─ fold_observable_system.candidate_observables    the grammar
       ├─ fold_observable_system.acquire_closure          closure per candidate
       │    └─ finite_generator_problem_dna
       │         .discover_action_observable_basis        the actual closure prover
       ├─ representation_certificate.certify              admit / refuse, per task
       │    ├─ transition_check                           from the closure prover
       │    ├─ span_membership                            decides the read-out
       │    ├─ congruence_check                           per layer, per label
       │    └─ (start check)
       ├─ representation_certificate.same_span            candidates -> spaces
       ├─ representation_benchmarks.fold_search_comparison  probe measurement
       ├─ representation_policy.select                    Pareto fronts + gate
       ├─ _existing_route_entry                           the existing route competes
       ├─ (tie-break)                                     measured over the declared workload
       └─ answer_with / answer_with_concrete
            └─ quotient_counting.layered_count            the counting DP
  └─ self_directed_search.solve_from_store(task, book)    reuse, no acquisition
```

### 2.2 Single route, one process

```
scripts/run_route.py --task <name> --route {enumerate,concrete,represented}
  └─ representation_benchmarks.{enumerate_rung, concrete_merge_rung, represented_rung}
       └─ quotient_counting.{enumerate_count, layered_count}
```
`--route represented` reads the basis and matrices out of a ledger file and
acquires nothing. `--instrumented` turns the call counters on; without it
nothing is wrapped and the timings are of unmodified code.

### 2.3 Repeated timing, fresh process per measurement

```
scripts/measure_routes.py --task <name> --length N --repeat K --ledger <file>
  └─ subprocess -> scripts/run_route.py   (one process per route per pass)
```

### 2.4 Other entries that still work

- `scripts/run_self_directed_task.py` — one task, the earlier single-task entry.
- `scripts/evaluate_representations.py` — the evaluation-layer report
  (differential + fold), including the four-cause attribution ladder.
- `scripts/run_acquisition_session.py --config configs/*.json` — the older
  acquisition session (holonomic / fold / fold_observable domains).

### 6.2 What the run chose, and why that is not "nothing was learned"

For all three solvable tasks the tie-break — acquisition plus the cost of the
task's own declared workload, in wall time — selected the **existing exact
route**. The learned representation was on the same Pareto front and used 42×
fewer nodes, but the acquisition of 144 candidates cost 377 s against a 9.92 s
workload.

That does **not** mean nothing had to be learned. The run paid condition B in
full to find out. The earlier report's phrase "何も学習せずに解けた" is wrong for
that reason and is withdrawn (§9). With the workload set to n=14 alone, the same
tie-break selects the learned representation (17.88 s against 21.79 s).

## 7. What is proved, and what is only finite-checked

**Proved (symbolic, holds at every state):**

- `Phi(T_g(x)) = B_g Phi(x)` for every label — polynomial identity from
  `discover_action_observable_basis`. Scope: all finite words, linear closure of
  the supplied observations.
- The one-step correspondence between the kinematics and the 12×12 matrices —
  `verify_step`, 24 reachable frames × 4 letters = 96 identities with a
  **symbolic** centre, so every integer centre is covered.
- The read-out: the task's evaluated quantity lies in the linear span of the
  basis, decided exactly by rank, with the coefficients returned. This is a
  statement about every state.
- Vacuous legality, where the task declares it by construction.
- The counting lemma in `quotient_counting` — written out with its base case and
  one-step induction. **Implementer-supplied general knowledge, not a discovery
  of any run.**

**Finite-checked only (scope recorded in the record):**

- Legality congruence, where legality is not vacuous: searched over every legal
  word up to `--certificate-depth` (4 in the reported run), layer by layer. A
  refusal found this way is a proof of failure; an admission is only "no
  counterexample to that depth".
- The observable congruence fallback, used when the task cannot state its
  quantity as an expression. Same status.
- The differential recurrence: checked against
  `holonomic_route_discovery.coefficients` to a stated number of terms.
- The answers at n=10, 12, 14 were **not enumerated**. They rest on the
  certificate.

**Not proved at all — recorded as conjecture:**

- axis1: maximum = n, count = 2^n
- c1+c2: maximum = 2n−1, count = 4
- axis1-from-AG: maximum = n+2, count = 2^n

These agree at the six lengths computed. No proof for general n, and **no
novelty check has been done**.

## 8. Known defects, gaps, unverified things

1. `self_directed_search.solve` has an unused local `cost_of` left from the
   previous tie-break. Harmless, not removed because the reported run was
   already executing against that code.
2. `same_span` compares candidates pairwise. Fine for 144, would not scale to
   thousands.
3. The certificate's congruence search is exponential in the depth. Depth 4 over
   144 candidates is most of the 377 s acquisition.
4. The `represented` route's instrumented primitive count reads 0 because the
   sympy matrix arithmetic it uses is not wrapped. Node counts are the honest
   figure there; the records say so in `primitive_count_note`, but any new
   reader could still misread the zero.
5. The four-cause attribution ladder is an ordered decomposition. It is the
   marginal effect of each rung **in the stated order**, not a unique causal
   split.
6. The repository's other ~360 test modules were not run.
7. The evaluation layer (`evaluate_representations.py`) has not been re-run since
   the counting DP was rebuilt; its last output is from the earlier code and
   lives in `artifacts/research/mortra-representation-policy-20260912/`.
8. Nothing in this line of work had ever been committed before this handoff. The
   77 files in the import closure were all untracked.
